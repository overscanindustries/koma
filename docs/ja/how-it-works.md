# 仕組み

アドレスは2.40の実行時アドレスです。ステータスタグの定義は[features](../internals/evidence-ledger.md#status-tags)（英語）にあります。ファームウェアそのものの解説は[内部資料](../internals/README.md)（英語）にあります。

## ローダーとパッケージ

カメラを起動不能にしうる操作は、フラッシュへの書き込みだけです。そのためKomaがフラッシュに書き込むのは、小さなローダーと、あとから読み込めないSDドライバーの変更だけです。それ以外はすべて1つのパッケージファイル`GRMOD.BIN`にまとめ、ローダーが起動のたびに読み込みます。パッケージは数秒で入れ替えられ、カード上のパッケージはカードを抜けば外れます。

純正の工場用ADJローダーもカードからコードを実行できますが、電源を入れるたびにキー操作が必要です。Komaはこれを開発にだけ使います。

## 起動とローダーのフック

Monitorブートローダーは、アプリケーションをフラッシュからRAMにコピーし、`0x1c000`にジャンプします（[internals 02](../internals/02-boot-chain-and-monitor.md)）。アプリケーションはタスクを起動し、アップデートファイルを確認し、SDカードを調べてから、`0x281ee`にある`bl 0x282cc`に到達します。Komaファームウェアはこの1つの呼び出しを`bl 0x57f78`に変えます。これは使われないコード領域（Dcfsのセルフテスト部分、`0x57f74..0x580cc`）に置いたローダーです。ローダーはまず元の`0x282cc`を呼び、それからパッケージを読み込みます（`HW`）。

ローダーはファイルタスクを待ってパッケージを開き、長さ（最大64KiB）、ヘッダー、チェックサムを確認します。本体をカーネルプールから確保し、その中のインストーラーを呼びます。ファイルがない、短すぎる、チェックサムが合わないといった場合はそのまま戻り、純正と同じように起動を続けます。フックより前は何も変えていないので、アップデートの確認とカードの検出は純正のコードで動きます。ローダーはフラッシュに書き込めず、パッケージもフラッシュ用のルーチンを呼びません（[ビルド時のlint](#ビルド時のlint)を参照）。

イメージはさらに、`0x112578`にあるMakerNoteのバージョン書式を`Rev%4.4x`から固定のタグに書き換えます。これで、どのファームウェアで撮ったかがすべてのJPEGに記録されます。ファームウェアのヘッダーは`0240`のままなので、バージョン表示とUSBの`-VER`は`02.40`を返し、純正のアップデーターもカメラを受け付けます。

### Komaファームウェアのイメージ

これまでに2つのイメージをビルドし、書き込みました。1つ目はカード用ローダーだけを加えたものです。2つ目はSD 2.0・SDHC・SDXC対応と、内蔵メモリーへのフォールバックを加えたもので、Koma 1.0はこちらをインストールします。どちらもリリース前のビルドなので、写真のタグはリリース版のタグ`240K1.0`とは異なります（[バージョン](versioning.md)）。

`/ATA1`はファームウェア内でのカードの名前です。USB経由では同じボリュームが`/EXT0`になります。

| | 1つ目のイメージ（カード用ローダー） | SDHCイメージ、ビルド2b |
|---|---|---|
| 純正からの変更 | ローダーの配置領域、フック、タグ`Rev024M` | 1つ目のイメージ＋SD 2.0/SDHC/SDXCドライバー、`/IROM`フォールバック、タグ`240K2` |
| パッケージの読み込み元 | `/ATA1/GRMOD.BIN` | `/ATA1/GRMOD.BIN`、なければ`/IROM/GRMOD.BIN` |
| 差分 | 344Bの配置領域＋4Bのフック＋マーカー | 1つ目のイメージに対し、54か所で計2,052B |

SDHCイメージのドライバーは、SD 2.0カードを初期化し（CMD8、HCS付きACMD41、CSD v2）、大容量カードではブロックアドレッシングを使います。SDSCカードでは純正のドライバーのバイト列がそのまま動きます。純正のファイルシステムは、大容量カードを単独ではマウントしません。パッケージの`widefs`機能がFAT層をセクター番号方式に変換してマウントします。ローダーが動く時点ではカードがマウントされていないため、ローダーはSDHC・SDXCカードから`GRMOD.BIN`を読めません。パッケージは内蔵メモリーに置く必要があります。設計と検証：[analysis/sdhc/driver](../../analysis/sdhc/driver/README.md)、[widefs](../../analysis/sdhc/widefs/README.md)（英語）。

読み込み順（`HW`）：ローダーはまず`/ATA1/GRMOD.BIN`を試します。これが開けなかった場合に限り、（必要なら）`/IROM`をマウントし、`/IROM/GRMOD.BIN`を開きます。カード上のパッケージが常に優先されます。ファームウェアの書き込みは内蔵メモリーに触れないので、インストール済みのパッケージは書き換え後も残るはずです（`INFERRED`。パッケージを入れたまま書き換えた記録はまだありません）。

フラッシュイメージの形式とアップデーター：[internals 03](../internals/03-firmware-image-and-update-format.md)（英語）。

## GRMOD.BIN

```
header     'KMOD': offsets of records, init table, resident segment, relocations
installer  Thumb code                                          (transient)
records    each with the bytes it expects to replace           (transient)
inits      init table                                          (transient)
resident   manifest ('KOMA', build id, status, version string), feature code, tables
relocs     relocation table                                    (transient)
```

機能（feature）は4種類の変更を宣言します。どれも、書き換え前に想定されるバイト列（before-bytes）を持ちます。

- Patch：古いバイトの上に新しいバイトを書き込みます（コードまたはデータ）。
- Pointer：4バイト境界のワードを、常駐ラベルのアドレスに設定します。
- Redirect：1つの`bl`を、排他的にハンドラーへ向けます。
- Hook：`bl`をラップします。ハンドラーは元の引数を受け取り、次のリンクを呼びます。1つの箇所に複数の機能をチェーンでき、元の処理は1回だけ実行されます。

インストーラーは、まずすべてのbefore-bytesを検証します。次に常駐ブロックを配置し、すべての分岐の範囲を確認し、常駐コードをコピーして再配置し、各機能の初期化を実行します。そのあとで初めて、割り込みを禁止した状態ですべてのレコードを適用します。それより前に失敗した場合は、何も書き込みません。適用後、ローダーは一時的な部分を解放します。`koma04`は常駐ブロックをカーネルプールではなく固定アドレス`0x3dae00`にリンクし、その後ろに16バイトのカナリアを置きます。`koma04w`はそこに41,336Bを常駐させます（`HW`：`KOMALOG.TXT`が`RES 003DAE00`とカナリアの無事を報告）。

KOMA FEATURESがESSENTIALのとき、インストーラーは固定の必須リストにない機能の初期化とレコードをすべて飛ばします。

## ビルド時のlint

`koma build`は、次のルールに反するパッケージを拒否します（`tools/koma/linker.py`、`lint`）。

1. `FORBIDDEN_CALLS`に挙げたフラッシュ、調整値ストア、アップデーターのルーチンを、どのソースも読み込んだり、保持したり、呼び出したりしてはいけません。それらへの`bl`を作るパッチも、それらの呼び出しをラップするフックも禁止です。
2. 純正の設定バイトに書き込む機能は、書き込む値を宣言しなければなりません。唯一の例外は`settingsio`のインポートで、検証済みの`PARAM.DAT`をブロックの上にコピーします（`BULK_SETTINGS_WRITERS`）。
3. `0x281ee`より前に実行される32バイトのコードラインには、パッチ、フック、リダイレクト、ポインターを置いてはいけません。命令キャッシュに古いラインが残っていると、古いバイトが実行されるおそれがあるためです。一時的な診断機能`waitdiag`の6か所だけは、確認済みの例外として許可しています。呼び出しの最初のハーフワードだけが変わり、新旧のハーフワードがどう組み合わさっても正しいコードに到達するようにハンドラーの入口を配置しています（`EARLY_SITE_OK`）。

リンカーはこのほか、before-bytesの不一致、書き込みの重複、宣言した呼び出し先への`bl`ではない箇所へのフック、ほかの機能が変更するバイトに依存する機能、範囲外の分岐、Komaのバイト範囲外のメニュー項目も拒否します。問題はまとめて一度に列挙します。実行時に計算されるアドレスは、lintでは検出できません。

## 設定の保存

カメラは4,096バイトのユーザー設定ブロックを`0x1b000..0x1bfff`に持ち、電源オフ時に専用のルーチンでフラッシュに保存します（[internals 05](../internals/05-settings-and-adjustment-store.md)）。Komaは、純正が使っていないバイトを使います。

| アドレス | 内容 |
|---|---|
| `0x1b8b0` | マジック`KOMA`とバージョンバイト（`0x1b8b4`） |
| `0x1b8b5..0x1b8cf` | メニュー項目ごとに1バイト（項目の選択肢インデックス） |
| `0x1b8d0` | `KSIO`ヘッダー：設定I/Oのバージョン、7バイトのファームウェアタグ、最後のインポート結果 |
| `0x1b900` | ルックの保存領域`RCP6`：ヘッダーのあと、`0x1b910`からルックごとに12バイトのレコード |
| `0x1ba00` | ルックごとのGRAIN / VIGNETTEのバイト |

マジックがなければ、Komaは初期値を書き込み、最後にマジックを書きます。Komaは保存ルーチンを呼びません。Komaのバイトは、純正の電源オフ時の保存で保持されます。ルックが純正のIMG SETのバイトに純正以外の値を入れることはありません。そこにはNORMAL、B&W、B&W(TE)のいずれかを入れ、ルックのIDはKomaのバイトに持ちます。パッケージがなければ、カメラからは普通の純正の設定に見えます。

`settingsio`は起動のたびにブロックを`PARAM.CUR`にエクスポートし、有効な`PARAM.DAT`を1回だけインポートします（マジック`MG1H`、チェックサム、Komaのヘッダーのバージョンを確認）。インポートでは本体固有のバイトの表を読み飛ばし、Komaの各項目のバイトを範囲内に収め、結果を`KSIO`のステータスバイトに記録します。ほかのすべての機能の初期化のあとに実行されるので、エクスポートにはそれらの書き込みも含まれます。

## 現像処理

静止画は2回の現像パスで処理されます。Komaは、パス1（`0x96436`）とパス2（`0xafd3e`）で純正のモノクロ設定ライターを呼ぶ箇所をフックします。純正がレジスタ値を書き込んだあとです。パス2はホワイトバランス、色差、マトリクス、モノクロの設定を書き直すので、パス1だけで上書きした値は失われます。Komaは両方で書き込みます（`HW`）。

- モノクロのルックは、生成したトーンカーブを純正のテーブルアップロードで送り、フィルターの輝度ウェイトと調色ワードを設定し、セレクターのキャッシュを無効にして新しいテーブルを使わせます。シャープネスはフックしたゲッターから供給し、EXIFにも反映されます（`HW`）。
- カラーのルックは、下の表のカラーレジスタに書き込みます（POSITIVE、NEGATIVE、BLEACH、RETROは以前のビルドで撮ったフレームで`HW`）。
- SELECTとGRAIN/VIGNETTEは、JPEGエンコードの前に、`0x117382`で仕上がったマスターYUV画像に対するピクセル処理です。SELECTは、選んだ色相帯の外側の色差を打ち消します（`HW`）。GRAINとVIGNETTEはYプレーンを処理します（`EMU`）。

| レジスタ | 意味 | ステータス |
|---|---|---|
| `0x12018004` | 色差ゲイン、4バイト。0でグレーの画面になり、4つすべてを1.30倍すると一様に1.30倍。SATURATIONを担います。 | `HW` |
| `0x12018104`、`+4`、`+8` | 3x3カラーマトリクスの行（MatR、MatG、MatB）：符号と絶対値のバイト（ビット7が符号）、各要素は加算、バイト0が青。TINTはG行のシフトです。 | `HW` |
| `0x12018110`、`0x12018114` | ホワイトバランスの倍率。WARMTHは、そのショット自身のAWB値に対してRとBを倍率で調整します | `HW`（以前のフレーム） |
| `0x120180d8` | 色差のコアリング：Cb（下位フィールド）とCr（上位フィールド）のうち、フィールド値未満を除去します。オフセットではなく不感帯です | `HW` |
| `0x12018028`、`2c`、`30` | IQの色相マトリクス、クリップ、オフセット：書き込んでも効果なし | `HW` |

トーンカーブは全チャンネル共通の1本なので、クロスプロセスのようにチャンネルごとに変えるルックは作れません。ライブビューでは、ライブビューに戻るたびにリコーのモニター用プリセットが実行されます。`preview`機能は、その呼び出しのあとでルックの一部を適用し直します（`EMU`）。パイプラインの詳細：[internals 06](../internals/06-image-pipeline-and-color.md)。レジスタの調査：[colourprobe](../../analysis/koma-0.1/colourprobe.md)（いずれも英語）。

## メニュー

5タブのメニューは、純正のメニューにパッチを当てて作っています。リダイレクト、ポインター、パッチでタブの表、ヘッダーの描画、項目の表の参照先を変えます。Komaが描くヘッダー帯が、純正のタブの画像を覆います。Komaは純正のリスト描画とその文字セットを流用しているので、ラベルには純正フォントにある文字しか使えません。項目はデータ（ID、ラベル、選択肢、バイト、初期値、ページグループ）で、リンカーがページに割り付けます。そのため、機能はメニューのコードに触れずに項目を追加できます。確定時、Komaは変更された項目をすべて見つけて適用し、それからすべてのカーソルをそれぞれのバイトから読み直します。こうすることで、ほかの項目を動かす変更（ルックの選択、RESET）が上書きされません。別のメニュー構成（STK+KOMA、GR II）は、起動時にコピーされるデータのオーバーレイです。アプリケーションの構造：[internals 04](../internals/04-application-architecture.md)（英語）。

## USB

USB接続がORIGINALのとき、カメラはテキストコマンドと応答、データフレームからなるリコー独自のプロトコルで通信します（[internals 07](../internals/07-usb-protocol.md)、英語）。Komaは、`0x1fb400`にあるコマンド表の使われていないエントリーの参照先を変えて、コマンドを追加します。`-FDWL`は`-LVFR`に、`-SDIS`と`-GDIS`は`-KSET`と`-KGET`に、`-FUPL`は`-KSTA`に、`-PWOF`は`-PEEK`になります。各ハンドラーはUSBタスク内で動きます。

- テザー：純正はケーブルが接続されている間USBの状態を強制するので、`-CCTL keyset`によるキー操作は無視されます。アプリ状態の判定処理にある`0x4fe44`の排他的なリダイレクト1つで、`-CCTL remtin`のあとはダイヤルの状態を優先させます。これにより、USBセッションを維持したままキーとシャッターが使えます。`remtout`を送るかケーブルを抜くと、操作がカメラ側に戻ります。
- ライブビュー：`-LVFR <mode>,<seq>`は、ライブビューのリングバッファから1フレームを返します。モード0はグレー160x120、モード1はJPEG 320x240、モード2は画面表示（OSD）レイヤー（360x240、パレット付き4bpp。液晶が壊れた本体向け）、モード3はJPEG 640x240です。
- 設定：`-KSET`は、確認済みの範囲内でRAM上の設定バイトを1つ書き込み、適用します。`-KGET`は読み出し、`-KSTA`は状態のスナップショットを返し、`-PEEK`は`0x1a8000..0x3e5000`のRAMを読みます。
- テザー停止の修正：`remtout`のあとの2回目のリモートセッションが、液晶のミューテックスが保持されたままになるため約10〜20秒止まっていました。`stallfix`がこれを修正します。設定バイト1つで切り替えられます（`HW`。[原因の調査](../../analysis/stall/ROOT-CAUSE.md)、英語）。

ライブビュー配信の内部構造：[internals 13](../internals/13-display-live-view-and-usb-streaming.md)（英語）。

## エミュレーター

開発では、純正の2.40ファームウェアをUnicorn上で動かします（`tools/grdemu`）。周辺機器のモデル、仮想カード、UIレンダラー（`tools/grdui`）を備えています。実際の命令を実行するので、ファームウェアが書き込む値がわかり、カードを差し替える前にクラッシュやインストールの失敗を見つけられます。`koma smoke`は、ローダーイメージをパッケージ付きで起動し、1枚撮影して、すべての機能のフックを確認します。`koma selfcheck`は、より小さなユニットエミュレーターでインストーラーとフックを動かします。

エミュレーターでの結果には`EMU`のタグを付けます。機能が`HW`になるのは、カメラで動かしたあとだけです。詳細：[internals 10](../internals/10-emulator-and-tooling.md)（英語）。

## エミュレーターの限界

確認済みの差異（[emulator-limits](../../archive/research/emulator-limits.md)、英語）：

- CPU1はエミュレートしていません。2つ目のプロセッサーからの応答（電源、バッテリー、キー、レンズ）はすべて作り物なので、そのやり取りで起きる不具合（ADJのタイムアウトなど）は再現しません。
- センサー、AFE、レンズモーター、フラッシュ回路、実際の液晶はありません。レジスタが画像に与える効果は、カメラで測定する必要があります。
- 仮想時間は粗い単位です。競合状態、ウォッチドッグのタイムアウト、実際のスケジューラーのタイミングは再現せず、命令キャッシュの挙動もモデル化していません。
- OneNANDフラッシュのモデルは、ロック、不良ブロック、意図的に注入した失敗を扱いますが、電源断による書き込みの途中切れ、摩耗、ECCの生成は扱いません。
- 標準のハーネスは、ファイルAPIの境界で`/ATA1`をホストのフォルダーから提供します。SDHCファームウェアの検証に使ったSDモデルはレジスタレベルですが、タイミングは実際のカードと異なります。
- モデル化していないレジスタは最後に書き込まれた値を返すので、実際のレジスタ値に依存する挙動は異なる場合があります。
- ハードウェアの信号を介してファームウェアが読み込む画像（純正のタブの画像）は、描画結果に含まれません。
- 命令の細かな境界ケースでは、Unicornと実機のARMv4Tコアで挙動が異なる場合があります。
