# komabridge (Koma Setup over USB)

Implements phase B of [`archive/design/SETTINGS-EXTERNAL.md`](../../../archive/design/SETTINGS-EXTERNAL.md) (decisions 10 and 11), plus phase C's tether. A browser cannot use libusb, so `komabridge.py` is a small local HTTP server on top of `tools/grdusb` that lets `tools/komaset/web/koma-setup.html` read settings and photos from a GR DIGITAL in ORIGINAL USB mode, push one settings file back, and press the shutter over USB (with the Koma `tether` feature on the camera).

## Quickstart

    python3 tools/komaset/bridge/komabridge.py --real                          # the camera: power it ON first, then plug in USB
    python3 tools/komaset/bridge/komabridge.py --mock --mock-tether --mock-hw  # no camera: simulated, with the timings measured on the camera

Then open **http://localhost:8765/** (the bridge serves the Koma app from `tools/komaapp/dist`, and the old Koma Setup page at `/legacy`; without an app build, `/` is the old page). On the camera: SETUP, USB CONNECTION = ORIGINAL; turn
the camera on, then plug in the cable (plugged in while off, it boots into a state remote control cannot use).

## Hardware status

Tags: **HW** = done on a real GR DIGITAL (records in `analysis/hw-tests/`: `2026-11-07-spare.md`, `RUNBOOK-2026-11-08.md`, `RUNBOOK-2026-11-08-PM.md`, `tether-debug/FIX-1.4.md`); **STATIC** = read from the firmware, not run; **MOCK** = only against `mockcard.py` (or the emulator). The table was written after the 2026-11-07 runs: the selftest (`--real --selftest`) passed 9/9 twice in a row with tether 1.6 (build `64CE9496`) and 9/9 on build `747F061F` on 2026-11-08. The selftest calls the bridge's own endpoint functions, not its HTTP server. On 2026-11-08 the web page also ran against the cameras: a ten-minute task list passed 7 of 7, with 4 tether shots, 11 settings writes and 18 key taps, and no `/reboot` (`RUNBOOK-2026-11-08.md`). Rows below marked MOCK were not part of those runs.

## Run

    python3 tools/komaset/bridge/komabridge.py --mock     # simulated camera, safe anywhere
    python3 tools/komaset/bridge/komabridge.py --real     # a real camera; prints a warning first

    KOMA_FIRMWARE=firmware/original/gr-240.exe .venv/bin/python tools/komaset/bridge/komabridge.py --emu \
        [--module analysis/koma-0.4-candidate/koma04.grmod]   # the real 2.40 firmware + a module, in the emulator

With none of the three it refuses and exits 2. `--real` needs `pyusb` and `libusb` (as `tools/grdusb --live` does). Other options: `--port` (default 8765), `--quiet`, and for the mock `--mock-hw` (hardware timings measured on the camera: `MockBody.hw_timings()`, below), `--mock-reboot-s S` (how long the camera is away after a restart, default 4) and `--mock-stays-off` (it never comes back), and `--mock-tether` (the simulated camera has the Koma `tether` feature, so a full press adds a new `RIMGnnnn.JPG` about 1.5 s later; without it every `-CCTL` answers `200` and nothing appears, like a stock camera). The mock's card holds the owner's frames from `tools/komaapp/design/samples` (the `R00nnnnn.JPG` photos, and the `live-0n.jpg` frames as mode 1 live view, each held 4 s) when that folder is there; `--mock-patterns` keeps the drawn test photos and the moving live pattern (the look's CONTRAST and KEY and the EV byte then shape live view; the owner's frames are shown as they are). Every mock photo carries a SIMULATED MakerNote firmware tag (`mockcard.maker_app1`, the layout `onboardExif.js` reads): `Rev0240`, or `240K1.0` (a Koma 1.0 camera) with `--mock-koma`; `--mock-earlier` plays a Koma camera on an earlier build (tag `240K2`, shown by the app as "An earlier Koma build").

Then open `http://localhost:8765/` (the bridge serves the page itself), or `tools/komaset/web/koma-setup.html` by double-click. Opened as a file, the page finds the bridge at `http://localhost:8765` within a few seconds; `?bridge=PORT` points it elsewhere.

### Phone mode (`--lan`, or Settings > Use on your phone in the app)

    python3 tools/komaset/bridge/komabridge.py --mock --lan      # or --real --lan

Since 2026-11-08 (`phoneaccess.py`, APP-REDESIGN decision 17) phone mode switches at runtime: the app's Settings > Use on your phone turns it on and off, and `--lan` only turns it on at start. The loopback listener never changes (127.0.0.1, no token, the Host and Origin guards). Phone mode adds a second listener on this computer's network address and the same port (`lan_address()`); off by default. Its QR code (`qrmini.py`: a stdlib QR encoder, byte mode, level M, versions 1..6; the tests decode it with OpenCV where installed) carries `http://<address>:PORT/?pair=<code>`, a one-time pairing code: the phone's page trades it once (`POST /phone/pair`) for a token of its own, and the code is replaced at once, so a photo of the screen is useless after the phone has paired. From then on the token model is the one `--lan` always had: every request on the network listener must carry the token as `?token=` or an `X-Koma-Token` header (compared in constant time), or it gets `403` `code: token` with nothing sent to the camera; CORS preflights pass without it; with a valid token any `Host` and `Origin` is accepted (CORS reflects the origin); the app's files load without it. Revoke (`POST /phone/revoke`) signs every phone out and closes their open connections (a running live view ends) and makes a new code; Off (`POST /phone/off`) does the same and stops listening. `GET /phone`, On, Off and Revoke answer on the loopback listener only; a paired phone gets `403` `computer_only`. They also refuse any `Origin` but `http(s)://127.0.0.1` or `localhost` (`403` `origin`; `localguard.py`), so a web page in a sandboxed iframe (`Origin: null`, which the loopback listener otherwise lets through for the old page opened from disk) can neither turn phone mode on nor read the code. The pairing link opened on this computer itself pairs nothing (`404` `not_lan` with `local`, this computer's own address). `GET /phone` checks the network address again; after a change the listener moves to the new address with a new code and phones on the old one are signed out. Nothing survives a bridge restart. A paired phone can read the card and press the camera's buttons, so use a network you trust. MOCK only: never tried with a real phone.

Field setup for the broken-screen spare: the camera on USB to a Mac on the same Wi-Fi as the phone, or to a Pi Zero (or any small Linux board with pyusb/libusb) running `komabridge.py --real --lan` on a battery, with the phone joined to the same network (the Pi's own hotspot works). Open the printed URL or scan the QR code; Remote and Shoot work at phone width (Remote's buttons stack under the screen). Untested on a Pi and on a real camera.

On the camera: SETUP menu, USB CONNECTION = ORIGINAL, plug in the cable, power on. Mass-storage or PTP mode is reported by `/status` and the page says to switch.

### One-command hardware check (`--selftest`)

    python3 tools/komaset/bridge/komabridge.py --real --selftest --out ~/koma-session/
    python3 tools/komaset/bridge/komabridge.py --mock --mock-tether --selftest --out /tmp/koma-mock/   # simulated Koma camera
    python3 tools/komaset/bridge/komabridge.py --mock --selftest --out /tmp/koma-stock/               # simulated stock camera

No server: `selftest.py` runs the USB steps of `docs/koma/HW-SESSION-2026-11-07.md` once and exits (0 when no step failed, 1 otherwise). Steps, each PASS / FAIL / SKIP with its time: 1 connect (descriptors, `-VER`, USB speed if libusb exposes it), 2 `PARAM.CUR` pull (`komaset check`, KSIO tag and import status), 3 `KOMALOG.TXT` pull and decode (`tools/koma/features/telemetry.py`: build id, STAGE, POOL, RES/CANARY), 4 photos list, 5 timed `RETR` of the largest JPEG and of `PARAM.CUR`, 6 tether (`/tether/start`, one shoot with fetch, `/tether/stop`, MakerNote tag via `tools/spare_test/metadata.py`, expected `Rev024M`), 7 live view (30 pulls each of mode 0, 1, 2 inside remote control, at most 30 a second; fps, bytes/s, torn / sync-timeout / truncated counts, one saved frame per mode), 8 EV round-trip (`-KGET` byte `0x053`, `-KSET` to the next odd value, `-KGET`, restore, `-KGET`; `451 -KSET busy` is reported as busy), 9 `PARAM.CUR` and `KOMALOG.TXT` pulled again and diffed (`PARAM.CUR` must not change). Steps 6 to 8 run only when `KOMALOG.TXT` carries a Koma build id; a stock camera skips them ("needs Koma firmware"). A failed connect or a lost camera stops the run and the rest is SKIP; other failures are recorded and the run goes on. Remote control is always closed (`/tether/stop`) and the EV byte put back, also after an error.

It calls the bridge's own endpoint functions, so it sends nothing the allowlist does not already allow, and no `-STOR`, no `poff`. `--out` (default `~/koma-session`) gets `report.md` (steps, a summary table, a "Send back" list), `report.json`, `PARAM-1.CUR` / `PARAM-2.CUR`, `KOMALOG-1.TXT` / `KOMALOG-2.TXT`, `photos.json`, `tether-RIMGnnnn.JPG`, `live-mode0.png`, `live-mode1.jpg`, `live-mode2.png`. With `--mock --mock-tether` the simulated card also gets a SIMULATED `KOMALOG.TXT` (build `4B4D0400`, the emulator's POOL 1888) so the Koma steps run. `--emu` waits up to 180 s for the boot before step 1. Tests: `python3 tools/komaset/bridge/test_selftest.py`. Never run on a camera.

## Endpoints

All JSON except the photo bytes and the page. In loopback mode (the default) the bridge listens on 127.0.0.1 only, answers loopback clients only, requires `Host` to be `127.0.0.1:PORT` or `localhost:PORT` (DNS-rebinding guard), and only accepts `Origin` `null`, `file://`, `http://localhost[:p]` or `http://127.0.0.1[:p]` (CORS reflects that origin; Chrome's private-network preflight header is answered).

| Endpoint | What it does | USB traffic |
|---|---|---|
| `GET /` | The Koma app (`tools/komaapp/dist/index.html`), its files at `/assets/<name>` and top-level `/<name>` (exact names inside `dist`, no traversal). A browser page load (`Accept: text/html`) of an unknown address with no extension that is not a bridge path gets the app's index. Without a build, the old page. Served without the token in phone mode (no camera access) | None |
| `GET /legacy` | The old Koma Setup page (`web/koma-setup.html`), kept until D3 of `docs/koma/APP-REDESIGN.md` | None |
| `GET /status` | `connected`, `camera.firmware` (`02.40`) and `firmware_display` (`2.40`), `usb_mode`, `bridge_version`, `backend` (`mock`/`real`), `simulated`, `message`, `busy`, and `problem` while no camera is open: `usb` (no usable USB library), `two` (more than one Ricoh device), `open` (on the bus but could not be opened; `message` has the reason), `mode` (USB CONNECTION is not ORIGINAL), otherwise `null` | None while a session is open: polling only enumerates descriptors. On a new connection: bring-up and one `-VER` |
| `GET /settings` | `/EXT0/PARAM.CUR` as base64 plus the komaset `check` summary (size, magic, checksum, Koma header). 404 with `code: no_param_cur` if the card has none | `-NLST /EXT0`, `RETR /EXT0/PARAM.CUR` |
| `POST /settings` | Body `{"data": "<base64 of 4096 bytes>"}`. Envelope check with komaset's code (size 4096, magic `MG1H`, checksum); 422 with the check on failure, nothing sent. Then `-STOR` to `/EXT0/PARAM.DAT` and a byte-for-byte `RETR` read-back | `-STOR 4096 /EXT0/PARAM.DAT`, 1 data frame, `RETR /EXT0/PARAM.DAT` |
| `POST /reboot` | `-CCTL poff,5`. The bridge then drops its session | `-CCTL poff,5` |
| `GET /photos` | Every `.JPG` under `/EXT0/DCIM/*/` (the camera's folders are `NNNRICOH`, files `RIMGNNNN.JPG`): `path`, `folder`, `name`, `size`, `date` (from `-FDAT`, else the directory time), `width`/`height` (from `-INFO`). Newest first. `-INFO`/`-FDAT` results are cached per connection | `-NLST /EXT0/DCIM`, `-NLST` per folder, `-INFO` and `-FDAT` per new JPEG |
| `GET /photos?newest=1` | The newest JPEG alone, picked by the file time in its `-NLST` record, as the same record; `count` is every JPEG listed. For the Looks try-on, which needs one photo: a full listing costs `-INFO` and `-FDAT` per JPEG (75 ms each pair on HW), and the cache goes with every restart. MOCK only | `-NLST /EXT0/DCIM`, `-NLST` per folder, `-INFO` and `-FDAT` for that one JPEG |
| `POST /tether/start` | Remote control on: `-CCTL remtin`, then `-CCTL diaset,4` (virtual dial to still; dial 4 resolves to app state 2, [chapter 08](../../../docs/internals/08-card-scripts-and-service-terminal.md) (key and dial injection)). A `451` on `remtin` is tolerated (remote mode already on); `diaset` decides `ok`, and on failure `remtout` is sent so nothing is left half-on. Then `-LVFR 0` is polled until it answers 150, up to 15 s (`Link.lvfr_wait_s`); with no 150 3 s after the last arm it logs a `-KSTA` snapshot (run_state, app_state, remtin_flag, rec_dispatch, usb_attached) and re-arms (`remtin` + `diaset,4`), at most 3 times (hardware 2026-11-07: both can answer 200 and not take). `armed` says whether a 150 came; a shoot or focus re-arms once more and never presses a key without it (outcome `not_armed`, "Remote mode never armed"). No wait after the connect's `-VER` any more: `remtin` follows at once. A start still waiting for the camera lock when a `/tether/stop` arrives (a page closing mid-retry) does nothing and answers `ok: false, stopped: true` | `-CCTL remtin`, `-CCTL diaset,4`, `-LVFR 0` polls, `-KSTA` and re-arm pairs if needed |
| `POST /tether/shoot[?fetch=1]` | Lists the JPEGs, then half-press hold (`keyset,1,26`), 0.7 s for AF, full-press hold (`keyset,1,27`) for 0.3 s, release 27 then 26 (in a `finally`, so on every path; a refused release falls back to `keyset,0,2`). Then polls the listing (first after 1 s, then every 0.5 s, up to 10 s) for a JPEG that was not there before. `outcome`: `shot` with `photo` (same record as `/photos`; `?fetch=1` adds `jpeg`, base64, and warms the cache for `/photos/<path>`), `no_file` (watchdog: the release sequence runs again and `message` says the camera is probably on stock firmware), `not_armed` (no `-LVFR` 150 even after re-arming; no key pressed), or `refused` (a `-CCTL` answered non-200; keys released). Starts remote control itself if `/tether/start` was not called | the start pair if needed, `-NLST` of DCIM and each folder, 4 `-CCTL keyset`, then `-NLST` polls |
| `POST /tether/focus` | Half-press hold, 0.7 s, release (also in a `finally`) | `-CCTL keyset,1,26`, `keyset,0,27`, `keyset,0,26` |
| `POST /tether/interval` | Body `{"every_s": N, "count": M}` (N 1..86400 s, M 1..9999): M shoots, one every N s from the start, in a background thread, each through the `/tether/shoot` path (so each pauses the live stream and releases its keys on every path). A shoot that overruns the next slot delays that one (no catch-up burst); a `503` (camera lost) ends the run. 409 `code: interval_running` while one runs. `GET` returns `running`, `every_s`, `count`, `done`, `shots`, `failed`, `next_in_s`, `last` (`n`, `outcome`, `ok`, `photo`, `message`) and `ended` (`finished`, `cancelled`, `tether stopped`, `camera lost`); `DELETE` cancels between shoots (a shoot in progress finishes). `/status` carries the same as `interval`. Mock-tested only | as `/tether/shoot`, M times |
| `POST /tether/stop` | `-CCTL keyset,0,2` (every injected key up, virtual dial back to the real one; this is also what lets the v1.1 feature force the USB state again) then `remtout`. Always `ok`; the replies say what the camera did. The page also sends it by `sendBeacon` when it closes | `-CCTL keyset,0,2`, `-CCTL remtout` |
| `GET /live?mode=1` | Live view as `multipart/x-mixed-replace` (boundary `komalive`), one part per frame, so an `<img>` can show it. Each frame is one `-LVFR <mode>,<seq>` (seq counts up from 0, wrapping at 65535), at most 30 a second. Mode 1 (default): the camera sends the JPEG scan only; the bridge prepends the header and serves `image/jpeg`. Mode 0: 160x120 raw grey, served as `image/png` (stdlib `zlib`; simpler than a JPEG encoder, and `<img>` shows PNG parts the same way). The first frame is pulled before any header goes out, so a camera without live view gets JSON `409` `code: live_off` with the camera's `reply`. The stream ends on client disconnect, after `451` has lasted 3 s without a break (a shorter `451` is transient: the monitor restarts after a tethered shot, so the bridge retries every 100 ms and `/live/status` says `paused: true`, `reason: "camera busy"`), on any transport or protocol error (the multipart closes with `--komalive--`), when a newer `/live` starts, on `/live/stop` and on `/tether/stop`. Frames flagged truncated are skipped and counted | `-LVFR m,seq` per frame |
| `GET /live/frame?mode=1` | One frame, `image/jpeg` (mode 1) or `image/png` (mode 0), with `X-Frame-Seq` and `X-Frame-Truncated`. For debugging | one `-LVFR` |
| `GET /live?mode=2` | The camera's own screen layer (menus, icons): one `-LVFR 2,<seq>` per part, at most 5 a second, served as a 4-bit indexed `image/png` whose index 0 is transparent (Remote task; details below). Its own stream: it supersedes only an older mode 2 stream and runs next to a mode 1/0 stream. It does not need remote control: the firmware lane says mode 2 answers `150` in the stock USB state and while the monitor is stopped (menu open) | `-LVFR 2,seq` per part |
| `GET /live/status[?mode=2]` | Just the live counters (below) of the video stream, or of the OSD stream with `?mode=2`. No USB traffic, no lock | None |
| `POST /live/stop[?mode=1\|2]` | Ends the running streams; `?mode=1` (or 0) only the video one, `?mode=2` only the OSD one | None |
| `GET /keys` | The key codes the bridge may press: `keys` (code, firmware `name`, `panel` label or null, `inert` if the firmware ignores it when injected), `refused` (code, name, `why`), `actions` (0 release, 1 hold, 3 tap), `remote` (remote control on). No USB traffic | None |

**Auto Power Off keepalive (tether).** Tether v1.3 holds Auto Power Off by renewing it on every `-CCTL keyset`, but a record-side re-enable can still fire during a long idle after a shot. So while remote control is on (`/tether/start` ran on this connection) and no `-CCTL keyset` has been sent for 20 s (any action and code; other traffic does not count), it sends `-CCTL keyset,0,27` (a release of the unpressed full-press key: an allowlisted row, harmless) and logs it to stderr (`komabridge: keepalive after 60 s idle in remote control: ...`). A thread checks every 5 s; it waits up to 1 s for the camera lock (never behind a shoot for longer) and skips while a shoot or key press is waiting for the lock. A running live stream or an editing session (`-LVFR`/`-KSET` all the time) does not hold it off: the keepalive takes the lock between stream pulls (the stream loop steps aside for it without showing as paused), and the interval is `Link.keepalive_idle_s`. `Link.keepalive_tick()` is the testable step (`KeepaliveTest`). Mock-tested only.

Every `/tether/*` answer is JSON with `ok`, `message` and `replies`: the list of `{"command": "-CCTL ...", "reply": "200 ..."}` actually exchanged, so a `451` is visible. `/status` also reports `tether` (remote control on). A shoot holds the camera lock for its whole run (about 2 to 12 s once armed; up to about 30 s more if it has to arm first), and so does `/tether/start` while it waits for the camera to arm; `/status` answers `busy` meanwhile, without blocking.

`/status` also carries `osd`, the same counters for the mode 2 stream. Key and dial presses raise the same hold flag as a shoot, so they go in ahead of the streams' next pull.

`/status` (and `/live/status`) carry `live`: `running`, `mode`, `paused` (a shoot or focus holds the stream, or a mid-stream `451` is being retried) with `reason` (`shoot`, `camera busy` or null), `fps` and `bytes_per_s` (measured over the last 2 s of `-LVFR` payload bytes, header included), `frames`, `dropped` (truncated frames), `torn` (frames with header flag bit 3, the display slot moved during the read; modes 0/1), `sync_timeouts` (flag bit 1, the VD wait timed out), `note` (mode 2: `palette: ROM default`, below) and `ended` (`client`, `stopped`, `camera: 451 ...` or an error) once it stops.

### Live view details

- **Payload** (`archive/design/LIVEVIEW.md`, final): 16 bytes big-endian, then the frame. Offset 0 magic `LVFR`, 4 mode u8, 5 flags u8 (bit 0 truncated, bit 1 VD sync timed out, bit 2 OSD page B sent, bit 3 torn frame (modes 0/1), bit 4 OSD base register unrecognised (page A sent); `/live/frame` returns them as `X-Frame-Flags`), 6 seq u16, 8 width u16, 10 height u16, 12 length u16 (bytes after the header; must match what arrived, else `ProtocolError`), 14 scale u16. Wire: `-LVFR m,seq` -> `150 ...` -> channel-2 data frame(s) -> `250 ...`, read with the same code as `RETR`.
- **JPEG header (mode 1).** `firmware_jpeg_header(scale, w, h)` rebuilds the exact 193 bytes the movie recorder writes per AVI frame (`0x8986c`): SOI; APP0 `AVI1` (length 16, then zeros); DRI 0; DQT with table 0 then table 1, each the base table in zigzag order (`0x18c3b0` luma, `0x18c3f0` chroma: T.81 K.1/K.2) scaled by `0x11422c`: `q = ((scale * base >> 9) + 1) >> 1`, clamped to 1..255, base unchanged when scale is 0; SOF0 from the template at `0x1789dc` (8-bit, H x W from the payload, Y 2x1 Tq0, Cb/Cr 1x1 Tq1: 4:2:2); SOS from `0x1789ef`. The firmware writes no DHT; the bridge inserts the Annex K tables (bits and values as stored in the firmware at `0x17885a`/`0x17892a`) before SOS, because macOS ImageIO (`sips`) refuses a JPEG without DHT. Headers are cached per (scale, width, height).
- **Interleave with a shoot.** The stream takes the camera lock for one `-LVFR` at a time. `/tether/shoot` and `/tether/focus` raise a hold flag before they take the lock; the stream loop checks it before each pull and waits (polling every 50 ms) until the shoot is done, then resumes on the same connection. The flag exists because Python locks are not fair.
- **OSD page (mode 2).** Payload after the 16-byte header: the 4 bpp OSD page rows (high nibble = left pixel, `ceil(width / 2)` bytes per row; width and height from the header, which is authoritative: the firmware lane expects 320x240 = 38,400 bytes, the emulator's page is 360x240 at stride `0xb4`, and both decode). Palette, chosen by the header's scale field: **0** = none sent, the bridge uses `OSD_FIXED_PALETTE_RAW` (the 16 raw VEN palette registers read from the `tools/grdui` emulator with a menu open); **N > 0** = N entries of 4 bytes appended after the pixels, each the raw register for index 0..N-1 as a big-endian u32 (`Y<<16 | Cb<<8 | Cr`, Cb/Cr signed, `0x161d30`). Both paths are implemented; the firmware lane decides which it sends. The color conversion is `tools/grdui/display.py`'s `ycbcr_to_rgb` (copied, cited), entries past N render magenta as there, and index 0 is transparent (display.py's inference from `0x161f18` refusing index 0). The PNG is built without per-pixel work: PNG's 4-bit indexed rows use the same nibble order, so each page row goes in as is, with `PLTE` (16 colors) and `tRNS` (index 0 alpha 0, the rest opaque). Sizes are checked against the header (`ProtocolError` otherwise). The emulator shows the firmware rewriting palette entries 2, 7, 8, 9, 12 and 13 between the shooting screen and the menu, so the fixed palette is approximate on some screens; an appended palette is the accurate path.
- **ROM palette fallback (mode 2).** The firmware's frame is 43,280 bytes: 16 header + 43,200 pixels (360x240) + 64 palette (16 VEN registers read back). If entries 1..15 arrive all zero (register readback may not work on hardware), the bridge uses the firmware's ROM default table at `0x1fba30` (`OSD_ROM_PALETTE_RAW`, copied from the 2.40 image; word i taken as index i + 1, an inference from comparing with the emulator's registers) and the OSD status `note` says `palette: ROM default` (also `X-Frame-Note` on `/live/frame`). The page shows that note and "frames torn: n" in its rate line.
- `-LVFR` is a **read** verb: built by `read_command("-LVFR", "m,seq")` next to `RETR` (mode 0, 1 or 2, seq 0..65535 without leading zeros, nothing else), never by `write_command`, not in the allowlist.

The wire path is `/EXT0/...`; the camera maps `/EXT0` to the card `/ATA1` ([chapter 07](../../../docs/internals/07-usb-protocol.md)), so `/EXT0/PARAM.DAT` is the design doc's `/ATA1/PARAM.DAT`. The bridge reads only card paths (`/EXT0`, 8.3 names); internal memory (`/IROM`) is never read.

`-VER` is deliberately sent once per connection and never by polling: on hardware a `-VER` was followed by the main camera's screen going dark and its lamp blinking ([chapter 07](../../../docs/internals/07-usb-protocol.md), `-VER` side effect).

## The write allowlist

`WRITE_ALLOWLIST` in `komabridge.py` is the only source of row-listed write commands; the one range rule beside it is `-KSET` (below). It holds decision 11's two rows, the tether key sequence and the Remote key extension, every row spelled out in full (121 rows):

| Verb | The one argument it may carry |
|---|---|
| `-STOR` | `/EXT0/PARAM.DAT` (size must be 4096; the firmware deletes an existing file first) |
| `-CCTL` | `poff,5` |
| `-CCTL` | `remtin`, `remtout` |
| `-CCTL` | `diaset,N` for N = 0..8 (`/tether/start` sends 4; `/dial` any of them) |
| `-CCTL` | `keyset,A,C` for A in {0 release, 1 hold, 3 tap} and every key code C in 0..41 except 6, 7, 8, 9, 24, 36 (36 codes, including 2 clear all and 26/27 the shutter as before) |

Refused key codes, in every action: **6 POWER** (a press also posts power-off `0x720d`), **7 PLAY** and **8 USB** (excluded so USB cannot turn the camera off or change its USB mode; [chapter 07](../../../docs/internals/07-usb-protocol.md) (`-CCTL`) reads "code 7 pressed / 8 released becomes message `0x720d`"; PLAY's long hold can also post power-off), **9 AVJACK** (a jack level, not a button; injecting it may move the picture to the AV output, I), **24 QACCESS** and **36 DPUSH** (action 1 in state 9 calls `0xc4b64`, the switch to PTP mode). 6 and 9 go beyond the owner's list (7, 8, 24, 36): 6 is the real power key in the key table (the owner's "7 and 8 (power)" follows the handbook/07 sentence, but POWER is 6), and 9 is not a button. The codes that stay allowed but do nothing when injected (polarity 2, or generated from the wheel inputs: 3, 4, 5, 10, 17, 18, 19 MENU, 21, 25, 30, 31, 34, 35, 39, 40) are listed `inert` by `GET /keys`. Codes 0 and 1 are sink control codes (commit the virtual dial, set it to the real dial); they are allowed as part of "every code" and harmless (RAM only), but nothing in the bridge sends them.

**What this extension reaches, and why it is acceptable now.** With MENU/OK (23) and the arrows the host can walk the whole camera menu, FORMAT and RESTORE DEFAULTS included. That reach is the reason card-script key macros were rejected before: a blind macro could format a card or reset the camera with nobody seeing it. Here every press comes from a person looking at the camera's own menu through the OSD overlay (`/live?mode=2`), so the menu is sighted; the page says "This presses real buttons on the camera. FORMAT and RESTORE DEFAULTS are reachable from the menu." The bridge itself does not know which menu item is selected and cannot block a FORMAT; that guard is the person watching.

**The `-KSET` range rule (Looks and Exposure).** `-KSET <off>,<val>` writes one byte of the settings block in the camera's RAM (offsets relative to `0x1b000`, decimal, no leading zeros; `val` 0..255). It is the `ksettings` v1.1 verb (`analysis/ksettings/README.md`); it answers `200 -KSET <off>=<val>`, `451 -KSET range` / `451 -KSET value` / `451 -KSET busy`, `501` on syntax. `write_command("-KSET", ...)` builds it only where the firmware itself accepts it, from two tables:
- `KSET_WINDOW`, inclusive, any value 0..255: `0x8b5..0x8cf` (the Koma rows), `0x910..0x9ff` (the 20 recipe records) and `0xa00..0xa13` (the FX table). **All of `0x8d0..0x8ff`** (KSIO sub-header and its reserve) is refused, as are the recipe store header `0x900..0x90f` (a bad header makes Koma reset every recipe) and everything else in the block.
- `KSET_STOCK`, the stock whitelist with the exact values stock writes: EV `0x053` odd 1..25 (13 = 0.0), ISO `0x059` {0, 1, 2, 4, 6, 7, 8}, WB `0x054` {0..5, 7}, WB detail `0x0a6` 0..16, metering `0x050` {0, 1, 2}, IMG SET `0x030` 0..6, SETTING1/2 `0x031..0x036` 1..5, TE tone `0x1a9` {1, 2, 3, 4, 6}, TE density `0x1aa` 1..5. The camera runs its stock apply after each, so the change is live. It answers `451 -KSET busy` while its menu or ADJ screen is open, while it is not idle in still record or while its monitor is stopped (`/ram` maps that to 409 `camera_busy`). `0x05a` is not WB (unmapped legacy byte) and is refused.

`-KSTA` (ksettings 1.3, diagnostic) is a read built by `read_command` with no argument; `BridgeSession.ram_state()` and `ram_state(link)` send it and decode the frame with `ksta_decode` (version word `0x4b53LLNN`, then `KSTA_WORDS` in order, mirrored from `tools/koma/features/ksettings.py`; a layout the bridge does not know is a `ProtocolError`). No HTTP route uses it; `analysis/hw-tests/tether-debug/exit_probe.py` does. The mock answers it in any state (`MockBody.ksta_frame`, stand-in values). The self-test re-sends `diaset,4` and waits for `-LVFR 0` = 150 before step 7 when step 6's shoot ran `-INFO` / `RETR` inside the remote session (the camera drops live view after them).

RAM only; the camera saves the block at a normal power-off. `-KGET <off>,<len>` is a read built by `read_command` (len 1..4096 inside the block). `test_komabridge.py` `KsetAllowlistTest` checks `0x900` and every byte of `0x8d0..0x8ff` refused, `0x8c0`, `0x8cf`, `0x910`, `0xa13` accepted, every stock byte against every value 0..255 (EV 14 refused, 15 accepted; ISO 3 refused; `0x05a` refused), and malformed arguments.

`write_command(verb, argument)` raises `WriteRefused` for anything else, with no override flag. `DELE`, `RMD`, `RNFR`/`RNTO`, `MKD`, `-ABOR`, `CWD`, `-FMT`, every other `-CCTL` (the refused key codes 6/7/8/9/24/36, codes above 41, action 2, `diaset,9`, extra arguments, leading zeros, spaces, upper case, embedded CR LF), `-STOR` to any other path (`PARAM.CUR`, `QRFLECT3`, `SCRIPT.MG1`, `/IROM/...`, `/ATA1/...`, lower case) and `-STOR` of any other size are all refused; `test_komabridge.py` checks each. Reads go through grdusb's own read-only builders (`-VER`, `-NLST`, `RETR`) or `read_command` (`PWD`, `-INFO`, `-FDAT`), which refuses write verbs and non-card paths. `BridgeSession` has no generic send. Firmware staging (`grdusb stage-update`) is untouched; the bridge borrows only its data-frame encoder and reply constants.

## Timings and robustness (what the page relies on)

- **Arming (HW).** `/tether/start` and every shoot/focus that has to arm first can take up to 30 s on a second session. The page gives the request 45 s and shows "Camera waking up for remote control, N s" with a progress bar; it reports a failure only when the bridge does (`armed: false`, `outcome: not_armed`).
- **After a shot (HW).** Live view comes back ~7 s after a tethered shot, and the shot's own `-INFO` / `RETR` drop it. With `rearm_after_read` (set by `main()` for the server; the selftest re-arms itself) `Link.run` sends `diaset,<dial>` after any request that read the card while remote control was on (`read_rearms` counts them), and the stream treats a `451` as transient for `live_off_grace_s` = 10 s (was 3 s), reporting `paused` / `camera busy` meanwhile.
- **EV busy window (HW).** `ram_write` retries `451 -KSET busy` for 5 s (`kset_busy_wait_s`) and lets live view run between tries; the page keeps the wanted value on screen and sends it again every second for up to 25 s.
- **Two tabs (MOCK).** `GET /live?cid=<tab id>`; `/live/status` reports the running stream's `client`, so a tab whose stream another tab took over says so and does not take it back.
- **`--mock-hw` / `MockBody.hw_timings(scale)` (MOCK of HW numbers).** Fresh-boot arm 0.8 s, later arms 20 s (a diaset re-sent while one is pending does not restart it), stock `-KSET` busy 7 s after the last one, live view back 7 s after a full press, a RETR / `-INFO` / `-FDAT` in remote control drops live view until the next diaset, RETR paced at 3.9 MB/s, `-INFO` + `-FDAT` 75 ms a photo (100 in 7.5 s). `MockBody.unplug()` / `plug()` simulate the cable or the power switch.

## Still unproven on hardware

- **The page and the HTTP server against a camera.** All page flows are MOCK (headless Chrome, `../web/test_e2e_browser.py`). The selftest proved the bridge functions underneath.
- **Remote keys other than the shutter** (menu navigation, dial positions): replies `200` were seen for `keyset,3,22`, `1,26`, `1,27`; what the camera's UI does with the rest is unobserved. `-LVFR 2` palette readback: the ROM fallback below exists because register readback may not work.
- **Looks live** (`-KSET` of `0x8b5..0x8cf`, the recipe records and the FX table) and the stock bytes other than EV: only EV was sent on a camera.
- **Why a second session arms slowly** (root cause pending; `-KSTA` waitdiag is the probe). The bridge works around it, it does not fix it.
- **Auto Power Off while tethered.** Tether renews APO on every keyset and the bridge sends a keepalive after 20 s idle; set Auto Power Off to its longest anyway.
- **Keyset code 8 (fake attach/detach) is deliberately not allowlisted**, nor 6, 7, 9, 24 and 36 (see the allowlist).
- **`-CCTL poff`.** Never sent on hardware. The bridge accepts a `451` reply as well as `200` (see "The emulator backend", poff). Static reading: `mg1_poff` `0x661b0` saves CONFIG and arms a reboot. Whether the camera comes back to a USB session afterwards is unknown; the page waits 45 s, then says to turn it on by hand.
- **`-SRET` and `-PRET`** are not used. `?thumb=1` fetches the whole file with `RETR` (about 0.9 s per photo on the camera) and cuts the thumbnail out on the host.

The remote tests cover the mode 2 decode of the emulator's menu page (PNG size 360x240, 4-bit indexed, `tRNS` = index 0 only, every index count equal to the page's nibble histogram, menu colors) and of a synthetic 320x240 page with the fixed palette, size checks, a short appended palette; the allowlist (each navigation key in actions 0/1/3 builds, action 2 refused, 6/7/8/9/24/36 refused in every action); `/keys`, `/keys/tap` and `/dial` refused (409) outside remote control and again after `/tether/stop`, refused codes 403 and bad bodies 400 with nothing sent; taps send no release, hold/release and the dial; `/live?mode=2` parts in the stock USB state and while the mock's menu has stopped the monitor (mode 1 `409` meanwhile), the stream following a DOWN; and the OSD and video streams running together, `/live/stop?mode=1` ending only the video, `/tether/stop` both. Every endpoint over real HTTP against the mock, the allowlist refusals, envelope rejection (bad checksum, bad magic, short block, not base64), the Origin/Host guards, the preflight, `-VER` sent once across repeated polls, and that no simulated transport logged a violation.


**Live-view pull timeout.** grdusb's transport reads and writes with a fixed 6000 ms per USB transfer (`TIMEOUT_MS` in `tools/grdusb/transport.py`), and neither `Session` nor the transport exposes a per-call timeout. A worst-case `-LVFR` pull with a hung engine could take about 6.3 s, so it can hit that 6 s limit and surface as a transport timeout, which ends the stream. The wish is an 8000 ms read timeout for `-LVFR` only; it is not done, because the bridge may not edit grdusb and a global change would loosen every other command. Do it in grdusb when the camera shows such pulls.

## The emulator backend (`--emu`)

`emulink.py` boots the real 2.40 firmware with a Koma module in the Koma emulator (`tools/koma/emu`, Unicorn) once, exactly as `analysis/tether-feature/scenario.py` does (module-loader image built in memory, the module as `/ATA1/GRMOD.BIN` on the modelled card, feature smoke stubs, internal memory formatted with the menu keys, USB attach by the real `0x131b3a(0)`), and then serves the bridge the same transport interface as the mock: `write()` takes host frames, `read()` hands back camera frames. **Simulated; not camera evidence.** Needs `KOMA_FIRMWARE` and `unicorn` (the repo's `.venv`). `/status` reports `backend: "emu"`, `simulated: true` and an `emu` block (`ready`, `booting`, `boots`, `boot` details, per-verb `routes` and `timings`). Until the first boot is done (about 70 to 90 s) the bridge reports no camera.

**How a command reaches the firmware.** Every command line goes through the firmware's own command state machine `0xcb6c4` (parser `0xcbd64`, dispatcher `0xcc304`, the stock or module handler), called in tOpeMain's poll context with the events the USB task would send, as the firmware self-test `0x53b52` and the live-view scenario do: `0x11` command, `0x10` reply sent, `0x20` data frame sent (each channel-2 frame is read from the state machine's output pointer, payload at `+8`), `0x21` data frame received (for `-STOR`). Replies and frames are wrapped in camera frames for grdusb's `FrameReader`, so `BridgeSession` runs unchanged. All Unicorn work runs on one worker thread; HTTP threads submit and wait (120 s per exchange).

| Verb | Route | Notes |
|---|---|---|
| `-VER`, `PWD`, `RETR`, `-INFO`, `-FDAT` | firmware | `-INFO` on `PARAM.CUR` answers `W=0 H=0`; `-FDAT` answers `date=` (no clock in the model) |
| `-STOR` | firmware | the 150 / data / 250 handshake is the firmware's; data arrives in 0x200-byte pieces (stack room); the block writer `0x56204` is routed to the card model (below) |
| `-CCTL` (remtin, diaset, keyset, remtout, poff) | firmware | `0xcd000` with the module's tether handler; every remtin/diaset/keyset/remtout reply in the test run was `200`, poff `451` (below) |
| `-LVFR 0/1/2` | firmware | the module's handler; engine stand-ins as `analysis/liveview/build/scenario.py`, armed only around `-LVFR` |
| `-NLST` | **host** | the firmware's directory walk needs the FAT code, which the model does not have: through the firmware `-NLST /EXT0` answers 150/250 with an empty listing. The host lists the modelled card's files (root only; there is no `DCIM`, so `/photos` is always empty) |

Stand-ins (not the firmware): the USB controller, qDCX queue, receive path `0xcaf74` and frame build `0xcb0d4` are bypassed; command text and upload pieces sit on tOpeMain's stack below a 0x240-byte frame; the card is grdemu's `FileLayer` (root files of `/ATA1` in memory, no FAT, no directories), plus `0x56204` (the writer `-STOR` uses, which FileLayer does not stub) routed to FileLayer's write for FileLayer's descriptors; `[0x1bd2d0]`/`[0x1bd308]` are set if the boot left them unset (it did not, in the runs here); live view as the liveview lane (semaphores return at once, `0x1201c018 = 2000`, `0x1200c16c = 0x300`, `FF D9` at the scan end, CC1 VD model running only during `-LVFR`).

**Monitor start.** After `diaset,4` the live-view monitor needs some 4e7 instructions to start in the model; a `-LVFR 0/1` pulled at once answers `451 -LVFR off`. The test waits 5 s of idle after `/tether/start`; the page's stream rides it out with its 3 s 451 grace.

**Time.** The emulator only runs when the bridge asks for something: before each command it runs for the wall time the bridge was idle since the last exchange ended, at 1.5e7 instructions a second, at least 2e6 and at most 6e7 (about 4 s of idle). A key tap therefore needs a few seconds of idle (or a few pulls) before its effect is on the screen; the OSD stream's own pulls provide that.

**poff.** `-CCTL poff,5` goes to the firmware handler, which answered `451 -CCTL poff command failure` in the model: `mg1_poff` failed saving `CONFIG.TST` before the restart post `0x66ab4` (`/status` `emu.poff` records whether `0x66ab4` ran). Static reading of 2.40: `0xcd000` answers 200 only when `mg1_poff` returns 0, but `mg1_poff` returns 2 after a successful save and restart post, and -1 on failure, so **on a camera `poff` may answer 451 even when it worked**. The bridge therefore accepts 200 and 451 from `poff` (drops its session either way, and with 451 adds a note to watch the camera); anything else is still an error. Then the emulator is rebooted from scratch with the card contents kept, so the module's boot import of `PARAM.DAT` runs for real. Everything else in RAM starts from the model's defaults again (its flash is erased): a setting that was not in an imported `PARAM.DAT` does not survive the reboot.

**What does not work in `--emu`.** A tethered shot does not produce a JPEG: the keyset path runs (`keyset,1,26`/`1,27` and the releases answer `200` through the firmware) but the model's capture pipeline never writes a file and there is no `DCIM`, so `/tether/shoot` ends `no_file` after its 10 s watchdog (the liveview and tether lanes could not get a shot through `-CCTL` in this harness either). Mode 1 frames are a rebuilt header plus whatever the stubbed JPEG engine left in the scan buffer (no sensor, no encoder): `image/jpeg` that starts with `FF D8` and ends with `FF D9` but does not decode. Mode 0 is the ring's contents (no sensor). `PARAM.CUR` from the model fails the checksum check (the stored word is stale against the default block; the module exports the RAM block as it is), so the page shows it as damaged; a pushed file with a correct checksum imports fine. Photos, `-INFO` sizes of real JPEGs and `-FDAT` dates cannot be exercised.

**Integration test.** `test_emu_integration.py` (skipped unless `KOMA_FIRMWARE` is set and the emulator imports), one boot, through the HTTP API: `/status` (emu, simulated, 02.40), `GET /settings` (the module's PARAM.CUR with KSIO), `POST /settings` with MENU LAYOUT (`0x8bb`) flipped and the checksum fixed, `POST /reboot`, wait for the second boot, `GET /settings` again: `PARAM.OK` = `OK`, KSIO status (`0x8dc`) 1, the flipped byte present; `/tether/start`, `/live/frame?mode=0` (160x120 PNG) and `mode=1` (`FF D8 .. FF D9`, not decodable); a mode 2 frame, `/keys/tap` MENU/OK (23), then the first part of `/live?mode=2` shows the menu (more than 2 % drawn pixels, different from before the tap; saved as PNG); `/tether/shoot` (all keysets `200`, outcome `no_file`) and `/tether/stop`. `EMU_SHOTS=<dir>` picks where the PNGs go.

    KOMA_FIRMWARE=firmware/original/gr-240.exe EMU_SHOTS=/tmp/shots .venv/bin/python tools/komaset/bridge/test_emu_integration.py

Timings from the passing run (2026-11-07, this Mac, wall seconds through HTTP): first boot to `/status` connected 72; `GET /settings` 0.5 to 0.6; `POST /settings` (with the tag check's read, `-STOR`, read-back) 2.1; `POST /reboot` to connected again 67; `/tether/start` 0.7; `/live/frame?mode=0` 4.2 (the first pull after 5 s idle carries the capped 6e7 advance), `mode=1` 0.5, `mode=2` 0.35; `/keys/tap` 0.2; first `/live?mode=2` part after 5 s idle 3.5; `/tether/shoot` 17 (10 s watchdog, `no_file`); `/tether/stop` 5.5. ## Big cards

- HW 2026-11-08: on a 64 GB card (widefs FAT32) `-NLST /EXT0` (card root) times out after 6 s and drops the session; `-NLST /EXT0/DCIM`, `RETR /EXT0/PARAM.CUR` and `RETR /EXT0/KOMALOG.TXT` work, and a missing file answers `450 Open error` at once.
- Rule: the bridge and the selftest never list the card root. Root files are fetched by RETR and `450` means absent (`read_root_file`). Subdirectory listings (DCIM, 100RICOH) are unchanged.
- The selftest takes the Koma build id from KOMALOG.TXT; if that is missing it asks `-KSTA` before it skips steps 6-8.

## Shot settle and Photos while Remote is on

- Shot settle (HW 2026-11-08, 0.3.2): after the keys, a tethered shot touches no card file until `-KSTA` shows `cam_state` 2 and `monitor_run` 1 (after `cam_state` 6 or 9 was seen, or after `SETTLE_UNSEEN_S` 1.5 s), then waits `SETTLE_DELAY_S` 1.5 s and lists 100RICOH once; a missing file is retried every `SETTLE_LIST_RETRY_S` 2 s up to the 30 s window. `-KSTA` is polled every `SETTLE_KSTA_POLL_S` 0.3 s. Log line: `shot settled after N s`. Reason: a card command during the camera's write corrupted 1 of 3 shots on the spare. The interval shooter and selftest step 6 use the same path.
- Photos while Remote is on (HW 2026-11-08, 0.3.2): `GET /photos` and `GET /photos/<F>/<N>` (list, thumbnail, download) answer 409 `Remote mode is on. Leave Remote before reading photos.` while tether is active. A card read in shooting state drops live view and the stream then ran at about 1 fps. The drop-and-rearm path stays for other reads (the shot confirmation). The check runs again under the link's lock (`guard=True`, the Photos lane 2026-11-08, MOCK): a request that passed it while `/tether/start` was waiting for the lock is refused instead of reading with remote control on. The Photos import's own list and reads are guarded the same way.
