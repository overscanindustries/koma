# Koma Setup (web)

**Quickstart.** `python3 tools/komaset/bridge/komabridge.py --real` (camera powered on first, then the USB cable), or
`python3 tools/komaset/bridge/komabridge.py --mock --mock-tether --mock-hw` for the simulated camera with the
timings measured on the camera; then open **http://localhost:8765/**.

Tags below: **HW** = observed on a camera, **MOCK** = only against the simulated camera. The bridge functions under every USB feature are HW (`../bridge/README.md`, "Hardware status"). The page itself was driven against a real camera on 2026-11-08: the ten-minute task list passed 7 of 7 (`analysis/hw-tests/WEBAPP-WRITE-AUDIT.md`) and Remote view and key taps ran on the spare. Other page flows, including Looks live editing, are MOCK (`test_e2e_browser.py`, headless Chrome, with the mock running the measured timings).

`koma-setup.html` is a single-file page for changing a Ricoh GR's settings on a computer. It works on the 4 KB settings file the camera writes to the memory card (`PARAM.CUR`) and produces the file the camera loads at the next start (`PARAM.DAT`). No server, no build, no network for the card-file tasks; the optional USB features talk only to the local bridge on this computer (see USB below).

## Open it

- Double-click `koma-setup.html`. Browsers block reading `../settings-map.json` from `file://`, so the page uses the copy of `settings-map.json` embedded in it and shows a quiet banner ("Settings list not loaded from disk..."). To use a newer list, open **Advanced** in the footer and use **Choose settings list**.
- Or serve the folder: `cd tools/komaset && python3 -m http.server 8000`, then open `http://localhost:8000/web/koma-setup.html`. The page fetches `../settings-map.json` itself and the banner stays hidden.
- Or open it from the bridge: `komabridge.py` serves the page at `http://localhost:8765/` (and the map at `/settings-map.json`), which is also how a phone opens it in phone mode (`--lan`, below).
- If the fetched list cannot be read (for example an unsupported checksum or field type), the page says so and does not fall back to the embedded copy; backup and restore still work.

The page stores only the last Advanced tab, whether the Shoot and live view notes were seen, and the picture-aid settings (`koma.overlays`) in `localStorage` (every access in try/catch). Nothing is uploaded.

## What the user sees

The home page offers nine tasks (Review photos, Shoot and Remote need a camera on USB; Looks works live with one and on a file without; Set up a card is always available). Task screens never show offsets, hex, raw values or file-format words; file names appear only as muted hints under file pickers and save buttons.

1. **Copy settings to another camera** (three steps). From: load the first camera's file. To: load the second camera's file. Review and save: a list of what will change grouped by menu page ("ISO SETTING: AUTO -> ISO 800"), a count of camera-specific items kept (expandable, with reasons in plain words), then **Save settings for the other camera** and the "On the camera" steps. Underneath, `mergeInto` applies the map's `exclude_on_merge` list, never copies the magic or checksum, and recomputes the checksum. If the two files carry different Koma versions, a warning and a **Copy anyway** checkbox appear (this is the CLI's `--force`).
2. **Change settings**. Load one file, then a menu-like editor: page list (SHOOTING, SETUP, KEY CUSTOM, PLAYBACK, MY SETTINGS 1/2, LOOKS, KOMA), sections as sub-headings, the camera label with the map's help sentence under it, and a control on the right (segmented buttons for up to five short options, a select otherwise, a stepper for numbers, switches for bitfields). Changed rows get an accent bar and **Undo**. Search filters across all pages. The sticky bar shows the change count and **Save to memory card**, which opens the "On the camera" sheet.
3. **Choose your Koma mode**. Cards for the `menu_layout` and `koma_features` fields. Without those fields: "Your Koma version does not have modes yet."
4. **Back up or restore**. **Download a backup** saves the same bytes as `GR-settings-YYYY-MM-DD.dat`. **Restore from a backup** saves a backup unchanged as `PARAM.DAT` and shows the camera steps.

5. **Review photos** (only with a camera connected by USB; otherwise the card says "Connect a camera to use this"). A grid of the card's JPEGs with name and date, newest first; click for a full-size lightbox with **Download**. Nothing else: no delete. A **Take a photo** link next to Refresh opens Shoot.
6. **Shoot** (only with a camera connected by USB). A big **Take a photo** button and a secondary **Focus**, a status line, the last shot shown large as soon as the camera saves it (click it for the lightbox), a strip of this session's shots underneath, and **Download**. The first time, a note says it needs Koma firmware with the tether feature and that stock firmware answers but does not fire (dismissed with **Got it** or by the first photo that arrives; remembered in `localStorage`). If no photo arrives, the page says the camera is probably on stock firmware, so the shutter did not fire; a collapsed "What the camera answered" shows the raw replies. Above the button, a live view panel: **Start live view** shows the camera's picture (an `<img>` on the bridge's `/live?mode=1`) with a small "26 frames a second, 44 KB a second" readout (`/live/status` once a second); **Stop live view** ends it, and so does leaving the view, losing the camera or closing the page. While a photo is being taken the picture dims and says "Taking photo", then carries on. While live view runs, an fps counter sits in the frame's corner (from `/live/status`; the camera delivered 22-29 fps to the selftest, HW) and a switch picks **Picture 320 × 240** (mode 1, the camera's JPEG) or **Grey 160 × 120** (mode 0); switching keeps the last frame up until the new stream's first. If the camera stops sending (after a shot it comes back in about 7 s, HW; a card read drops it until the bridge re-arms, HW), the picture dims with "The camera is busy... comes back by itself", and if the stream ends the page asks again with growing pauses (and re-arms after the second try), up to 6 times before it says the camera is not sending live view. Live view stays wanted across a lost camera, a bridge restart and leaving the view, and comes back by itself (MOCK). The first time, a note says live view needs Koma firmware with the live view and tether features (remembered in `localStorage`). Under the live view, a collapsed **Exposure** panel (also in Remote, under the picture aids): EXPOSURE COMP. as a slider in the camera's 1/3 steps from -2.0 to +2.0 (the readout is the camera's label), ISO SETTING as segmented buttons (AUTO, 64, 100, 200, 400, 800, 1600), WHITE BALANCE as a menu (with WB DETAIL 0..16 when it is DETAIL), PHOTOMETRY as MULTI / CENTER / SPOT, IMG SET as a menu in the camera's order, and the line "Changes apply on the camera right away and are kept when it is switched off normally." Labels and option names come from the map.

7. **Remote** (only with a camera connected by USB). For a camera whose own screen is broken: the camera's screen and its buttons. A 4:3 box at twice the camera's 320x240 shows the live picture (`/live?mode=1`) with the camera's own menus and icons on top (`/live?mode=2`, about 5 a second, transparent where the camera draws nothing); a **Show menu overlay** switch (on by default) hides it and stops that stream. When a menu is open the camera stops its picture; the menu then shows on the dark box with "The picture pauses while a menu is open.", and the page asks for the picture again every 2 s until it comes back. Beside it a button panel laid out like the camera's back, after `tools/grdui/playground.html`: zoom W/T, the four arrows around MENU/OK, DISP and Delete, PLAY and ADJ shown but disabled (from here they could turn the camera off or change its USB connection), Half press and **Take a photo** (the Shoot endpoints), and a mode dial menu ("Still photos" is the default; the other positions are numbered, since which mark is which is not known). Keyboard: arrows, Enter for MENU/OK, Space for the shutter, Esc to go back (sends DISP). A warning line at the top: "This presses real buttons on the camera. FORMAT and RESTORE DEFAULTS are reachable from the menu." Presses are sent one at a time in order; a refused press shows "What the camera answered".

8. **Looks** (live with a camera on USB; otherwise on a loaded settings file). The 21 Koma looks (the camera's IMG SET list, Look IA 2026-11-08) in the camera's order: STANDARD, MONO, SOFT MONO, HARD MONO, HICON B&W, SHINJUKU, FILM 400, FINE 100, DENSE, NOIR, MATTE, SELECT, POSITIVE, NEGATIVE, SLIDE 50, WARM NEG, BLEACH, RETRO, CUSTOM 1-3 (each with its type: Black and white, Colour or Select colour, "ADJ lever" when the lever steps through it, and ACTIVE on the active one). Selecting one shows its values as controls with the camera's labels and help: CURVE, CONTRAST, KEY, SHADOW, HIGHLIGHT, the three type-specific rows (B&W: FILTER EFF., TONING, TONE LEVEL; colour: SATURATION, WARMTH, TINT; Select colour: COLOUR, RANGE, SATURATION, as the camera's menu relabels them) and SHARPNESS, with GRAIN, VIGNETTE and ADJ LEVER (ON / OFF: whether the ADJ lever steps through this look) beside them. **Make this the active look** sets the look the camera uses. ("Recipe" is the code name only: field ids `recipe_*`, the `RCP6` store.)
   - **Live** (camera connected): the page reads the recipe area of the camera's RAM (`GET /ram?off=0x8b0&len=356`), starts remote control and live view (the Shoot view's live panel is moved above the controls and moved back when Looks is left), and sends every change at once: 150 ms after the last control change, `POST /ram/batch` with only the bytes that differ from what the camera has. The camera's preview feature applies the active recipe to its monitor, so the picture shows the change (in the mock: CONTRAST and KEY). A "Save to camera" note says there is nothing more to press: the camera keeps the changes when switched off normally. A refused write puts the controls back to what the camera has and says so. A camera without the verbs gets "needs Koma firmware with live settings" and can still use the file path. **Work on a settings file instead** switches to offline.
   - **Offline**: load a settings file (no USB loader here), edit, **Save to memory card** writes `PARAM.DAT` with the checksum and opens the "On the camera" sheet; **Send to camera** appears too when a camera is connected. A file without a recipe store (a stock camera's) shows the starting values, and the first change writes an empty store first (what Koma's `store_fix` would write: header `RCP6` v6, records and FX table zero, active none), then the edited record.
   - Underneath (`tools/koma/features/bwrecipes.py`): record `0x910 + 12 (id - 1)` = p0..p8, kind, `0xa5`, xor of bytes 0..9 with `0x5a`; FX byte `0xa00 + id - 1` = `0x50 | grain | vignette << 2`; active id `0x8c0`; editor rows `0x8c1..0x8c9`, GRAIN `0x8cc`, VIGNETTE `0x8cd`, ADJ LEVER `0x8ce`; STANDARD (look 21) record `0xa1c`, FX byte `0xa14`; ADJ LEVER mask `0xa18..0xa1a` (bit id - 1) + check `0xa1b` (m0 ^ m1 ^ m2 ^ `0x5a`; a bad check reads as the default 7 looks). A record that fails the checks (store header, valid byte, xor, type, colour look, value ranges per type) shows the recipe's default, as `eff` does. Editing a recipe writes its record, and if it is the active one also the EDIT RECIPE rows (and its FX byte plus the GRAIN/VIGNETTE rows). Camera write order: active id first, then the rows, then the records (values, kind, valid byte, xor), then the FX table, because Koma's `sync` copies the rows into the active record whenever they differ: rows that are already new cannot be undone by a half-written record. `RCP_TABLE` in the page (defaults, per-type ranges and row labels) is checked against `bwrecipes` by the parity test.
   - Grain and vignette are applied when a photo is saved, not on the live view (the page says so).

9. **Set up a card** (always available, no camera needed). Three panels.
   - **Get the Koma file.** Served over http(s) (the bridge, or a static server), the page fetches the module from `../../analysis/koma-0.4-candidate/koma04.grmod` relative to itself (from the bridge, page at `/`, that is `/analysis/...`; from a static server at the repository root it falls back to `../../../analysis/...`). On `file://`, or when the fetch fails, it shows "Choose the module file you downloaded" with a file picker. Either way it computes the file's SHA-256 in the browser (`crypto.subtle`, or a small built-in JS SHA-256 where the browser has no `crypto.subtle`, as on a phone at the bridge's plain-http LAN address) and shows it next to the published one: from `../../analysis/koma-0.4-candidate/SHA256SUMS` when the page can fetch it, else the copy `make_demo.py` embeds (`moduleData`, refreshed on every run). **Save as GRMOD.BIN** saves it under the name the camera looks for; it stays disabled when the two fingerprints differ.
   - **Put it on the card.** Format the card in the camera; copy `GRMOD.BIN` to the top level; turn on. A warning box covers a camera still on stock firmware: it needs the loader first, which is a firmware flash, done only by following `docs/koma/HW-SESSION-2026-11-07.md` section 6 (linked relative to the repository; the bridge does not serve docs). The page never offers the loader file itself.
   - **Check a card.** **Choose the card** opens the File System Access directory picker where there is one (Chrome, Edge), else `<input webkitdirectory>` (Safari, Firefox); **Or choose the files one by one** takes single files (for browsers without folder picking, such as iOS). The page reads `KOMALOG.TXT`, `PARAM.CUR`, `PARAM.DAT`, `PARAM.OK` and `PARAM.BAD` from the top level and counts the JPEGs under `DCIM`, then runs a JS port of `../verify_session.py` (`vsRun`): the KOMALOG, PARAM.CUR and import-file checks with the same wording and the same OK / ATTENTION / MISSING verdicts, a one-line headline from its exit-code rule, and **Copy the report** (the CLI's text plus its SUMMARY line). The JPEG MakerNote firmware tag is not read (the line says so; the CLI reads it), and there is no baseline diff. Nothing on the card is written.
   - `?demo=setup` opens this view.

**Picture aids** (Shoot, Looks and Remote): a toolbar under the live picture with **Histogram** (brightness, about 5 a second, bottom left; clipped ends drawn red), **Zebra** from a brightness level (default 250, 200..255) and **Focus peaking** (Sobel on brightness, a threshold slider, edges drawn in a saturated red over the picture), both about 10 a second. Each frame is drawn small (at most 320 wide) into a work canvas and read with `getImageData`; the results go on separate canvases over the image, which is never touched. The video images carry `crossorigin="anonymous"` so a page opened from `file://` may read them (the bridge answers with `Access-Control-Allow-Origin`); if a browser still refuses, the aids switch off and say to open the page from the bridge. In Remote the zebra/peaking canvas sits between the picture and the camera's own menus. Checked in headless Chrome from `file://` and from the bridge origin.

Where the browser supports it (Chrome, Edge), saving opens a save dialog so the file can go straight to the card; elsewhere it downloads. The camera steps: copy the file to the top level of the card, insert it, power on and wait about ten seconds, power off, power on again. The camera renames the file to `PARAM.OK` or `PARAM.BAD`.

## USB (Phase B)

With the local bridge running (`python3 tools/komaset/bridge/komabridge.py --real`, or `--mock` for a simulated camera; see `../bridge/README.md`), the page can talk to a camera in ORIGINAL USB mode. It never touches USB itself; it calls `http://localhost:8765` (`?bridge=PORT` to change).

- **Connect help.** The how-to says to turn the camera on first and then plug in the cable (HW: plugged in while off it boots into a state remote control cannot use). In Review photos, Shoot and Remote the steps are shown open when the bridge does not answer, with "this page reconnects by itself".
- **Polling.** `GET /status` once whenever a view opens, then every 4 s while a task is open (and on home only while the bridge answers). The bridge answers polls from descriptor enumeration and sends `-VER` only once per connection.
- **File loading.** Every loader except "Restore from a backup" gains a second way in. Bridge not running: only a muted **Or connect by USB** link that opens a three-line how-to with the start command. Bridge running, no camera: "Connect the camera with a USB cable" with the USB CONNECTION = ORIGINAL hint (or a note that the camera is in the wrong USB mode). Camera connected: "Camera connected: GR, firmware 2.40" ("(simulated camera)" with `--mock`) and **Read settings from camera** (`GET /settings`). A card without `PARAM.CUR` gets a plain message that the camera needs a Koma version that shares settings. In the copy task, reading the same camera twice is refused with "This is the same camera as the first one."
- **Saving.** While a camera is connected, each save-for-the-camera button (copy, change, mode, restore) gets **Send to camera** as the primary (`POST /settings`), and the old button becomes **Save to memory card** (secondary). The copy task first re-reads the connected camera and refuses if it is not the camera chosen under To. After a send, a sheet says the camera needs to restart, with **Restart camera** (`POST /reboot`, `-CCTL poff`) and the note that it may stay off and need turning on and reconnecting by hand. The page then waits up to 45 s for the camera, re-reads its settings and says whether it took them. Whether a real camera returns to USB after `poff` is unknown (U).
- **Review photos.** `GET /photos`, thumbnails from `GET /photos/<folder>/<name>?thumb=1` (lazy-loaded), full size and Download from the same path without `thumb`.
- **Shoot.** Opening the view calls `POST /tether/start`; leaving it calls `POST /tether/stop`, and closing the page sends the same by `sendBeacon` (falling back to a `keepalive` fetch). **Take a photo** is `POST /tether/shoot`; the new photo is shown from `GET /photos/<folder>/<name>`. **Focus** is `POST /tether/focus`. The bridge releases every key itself on every path. **Live view** is `GET /live?mode=1` (or `mode=0`) as the `<img>` source after `/tether/start`; clearing the `src` closes the connection and `POST /live/stop` is sent too. The bridge pauses the stream during a shoot itself; the page only dims the picture. **Waking up (HW timing, MOCK page):** `/tether/start` gets 45 s; while it runs, Shoot and Remote show "Camera waking up for remote control, N s. This can take up to 30 seconds." with a progress bar and the shutter buttons held, because a second remote session takes about 20 s to arm on the camera. Only the bridge's own verdict (`armed: false` / `outcome: not_armed`, after 30 s) is reported as a failure, with what to try. A `503` from any call (camera gone) triggers an immediate status poll, so the page switches to "Connect the camera" at once. The new photo goes to the front of Review photos' list without re-reading the card (a full listing takes ~8 s for 100 photos, HW). **Two tabs (MOCK):** the live stream carries `?cid=`; a tab whose stream another tab took over says "Live view moved to another window" and does not take it back; if another tab switched remote control off, the next action switches it on again.
- **Interval (Shoot).** An **Interval** section under the shutter buttons: every N seconds, M photos, **Start**/**Stop**, a progress bar and "Photo 3 of 10. Next in 7 s.". The bridge runs the schedule itself (`POST /tether/interval`), the page polls `GET /tether/interval` once a second and **Stop** is `DELETE`; **Take a photo** and **Focus** are disabled while it runs. Leaving Shoot stops the run (remote control ends). Tested against the mock only (bridge test); the page part was not driven in a browser.
- **Live view rate line.** Shows "frames torn: n" when the camera flagged torn frames (header bit 3); Remote's line also shows "palette: ROM default" when the bridge had to use the ROM palette for the camera's screen layer.
- **Emulator.** `komabridge.py --emu` serves the real firmware in the emulator; the page treats it as a simulated camera. See `../bridge/README.md`, "The emulator backend".
- **Remote.** Opening the view calls `POST /tether/start` (after any stop calls from Shoot have landed, since both views share remote control); leaving it, losing the camera or closing the page sends `POST /tether/stop`, which ends both streams and lets every key go. Buttons and keys are `POST /keys/tap {"code": C}` (UP 11, DOWN 12, RIGHT 13, LEFT 14, MENU/OK 23, DISP 22, T 15, W 16, Delete 20, the key map of `tools/grdui/playground.py`), the dial is `POST /dial {"n": N}`, Half press and Take a photo are `/tether/focus` and `/tether/shoot`. `/live/status` and `/live/status?mode=2` once a second tell the page when a stream ended (the picture ends with a `451` while a menu is open), and it asks again. A `409 remote_off` from `/keys` (another tab switched remote control off) switches it on again and resends the press. The rate line shows "Picture N fps" (mode 1, the video) and "menus N a second" (mode 2: the camera's OSD/menu layer, which the bridge pulls about 5 times a second; it is not video). While the picture is paused by the camera (a menu is open, a shot is saved) it dims and "The picture pauses while a menu is open." shows. Status: `-LVFR` 1 and 2 pulls are HW (selftest); the Remote page, the menu keys and the dial are MOCK.
- **Exposure (Shoot and Remote).** Opening the panel, or entering the view with it open, reads `GET /ram?off=48&len=43` (`0x030..0x05a`) and `GET /ram?off=166&len=1` (`0x0a6`, WB detail) so the controls start at what the camera has; they stay disabled until then. Each change is `POST /ram {"off", "val"}` 150 ms after the last move (a slider drag sends once it settles), after remote control is on (the camera's idle check needs it). Values are the stored ones (EV odd 1..25 with 13 = 0.0; ISO 0, 1, 2, 4, 6, 7, 8; WB 0..5, 7; metering 2 MULTI, 0 CENTER, 1 SPOT; IMG SET 0..6), the bytes and values of the `ksettings` v1.1 stock whitelist that the bridge and camera enforce. A `409 camera_busy` keeps the new value on screen (optimistic) with "The camera is still busy with the last change. Sending again in a moment." and sends it again every second for up to 25 s (HW: `-KSET` is busy for up to ~9 s after an EV change; the bridge itself retries 5 s per request). Only after that does it show "Camera is busy. Close the camera's menu and try again." and put every control back to the last value the camera confirmed; other refusals say so at once. EV round trip by `-KGET`/`-KSET` is HW (selftest); this panel is MOCK. Checked in headless Chrome against `komabridge.py --mock --mock-tether`: opening read EV 0.0, three steps right wrote 19 (+1.0) and the mock's picture got brighter, ISO 400 wrote 6, and with the mock's menu opened by a MENU/OK tap the next EV step answered 409, showed the busy line and the slider stayed at +1.0.
- **Looks writes** go to `0x8b5..0x8cf`, the records and the FX table only: the camera refuses all of `0x8d0..0x8ff`.
- **Phone mode.** When the page is opened from the bridge at `/` (`SAME_ORIGIN`), it calls the bridge on its own origin and appends the `?token=` from its address to every request, image source and the `sendBeacon` stop (`bridgeUrl()`); the map comes from `/settings-map.json`. Field setup: run `komabridge.py --real --lan` on a Mac on the same Wi-Fi as the phone, or on a Pi Zero on a battery with the camera plugged in (the broken-screen spare), and open the printed URL or scan its QR code. At 390 px Remote's button panel stacks under the screen and the screen fills the width (checked in headless Chrome against the mock, from the bridge origin with the token).
- The header brand is hidden on home, so "Koma Setup" appears once there (the H1).

## Phone app (Add to Home Screen)

`manifest.webmanifest` (name "Koma Setup", `display: standalone`, `start_url` and `scope` `./`, theme and background `--bg`, an SVG icon plus 192 and 512 px PNGs as data URIs, the 512 also as `maskable`) and `sw.js` (a minimal offline worker) make the page installable. Both are added only when the page is served over http(s): on `file://` the page adds no manifest link and registers no worker. `make_demo.py` writes the manifest and embeds the icon (`<link rel="icon">` SVG and a 180 px `apple-touch-icon` PNG) from the page's `:root` tokens.

- **Offline.** The worker caches the page, the settings list and the manifest when it installs (from the bridge: `/`, `/settings-map.json`, `/manifest.webmanifest`; from a static server: `koma-setup.html`, `../settings-map.json`, `manifest.webmanifest`), plus the module and `SHA256SUMS` once the page has fetched them. It answers those from the network first and from the cache when the network fails or refuses; every other request (the bridge's camera calls) passes through untouched. So Copy, Change, Looks on a file, Set up a card and Back up open without a connection; the USB tasks need the bridge.
- **The code (token).** The home-screen app starts at `./` with no `?token=`. When the page is opened from the bridge with `?token=`, it remembers the token in `localStorage` (`koma.token`, this origin only) and reuses it when started without one. With no remembered token (a first start from the home screen, or a stale token after the bridge restarted, which answers 403), a one-line prompt in the header says "Enter the code from the bridge": paste the part after `token=` of the address the bridge printed (a whole address works too); the page saves it and reloads with it.
- **iPhone / iPad (Safari).** Start `komabridge.py --real --lan`, open the printed address (or scan its QR code) in Safari, tap Share, then **Add to Home Screen**, then Add. Home-screen apps on iOS keep their own storage, separate from Safari, so the first start from the icon may ask for the code once.
- **Android (Chrome).** Open the printed address in Chrome, open the menu (three dots), then **Add to Home screen** (or **Install app** when offered), then Add.
- **Limits.** Browsers allow service workers and `crypto.subtle` only in a secure context (https, or `localhost`); the bridge's LAN address is plain http, so on a phone the page still installs to the home screen and keeps its code, but it does not work offline there and the fingerprint uses the built-in JS SHA-256. On Android a plain-http address installs as a shortcut that opens in Chrome rather than a standalone window. Offline use works from `localhost` (and would from https).
- **Bridge side (not in this folder).** For the installed app to start from the bridge, the bridge has to serve `/manifest.webmanifest`, `/sw.js`, `/analysis/koma-0.4-candidate/koma04.grmod` and `.../SHA256SUMS`, and, in phone mode, the page, manifest and worker without the token (they hold no camera access; without that, a tokenless start from the home screen gets the 403 before the page can ask for the code, unless the worker already has the page cached). Until then those requests fail quietly: no manifest, no worker, and Set up a card falls back to the file picker.

Hardware status: all of this was exercised against the mock only (headless Chrome over CDP: read, change, send, restart and reconnect, photos and lightbox, same-camera refusal, live view with a shoot in the middle; Remote: picture with the emulator's shooting-screen icons on top, MENU/OK by keyboard opening the menu over the dark box, DOWN, Esc bringing the picture back). These page flows have not met a real camera yet; the bridge calls under them have (see the tags above).

**Advanced** (footer link) is the original engineer view: map picker with coverage stats, both files with magic/checksum/Koma status, a raw field editor with offsets, the merge button with force and include-excluded options, the raw diff, and a hex dump. It shares the files loaded in the tasks.

## Map keys the page uses

Besides the schema in `archive/design/SETTINGS-EXTERNAL.md`: optional `help` (one sentence under the label), `order` (menu position; fields without it sort by offset), `section` (sub-heading; fields without one go in an unnamed group, headed "Other" if it is not first), and `ui: "hidden"` (shown only in Advanced). `bytes` fields are also Advanced-only. A trailing `(I)` in labels and option names is hidden in the task views. `exclude_on_merge` reasons are shown as plain-language categories, not verbatim.

## Engine

The first `<script>` holds the engine (block parsing, checksum, field codec, merge, diff, plus the Advanced view). The checksum follows the map meta, verified on a real block on 2026-11-07: the sum of big-endian u16 halfwords over `0x000..0xffb`, stored as a 4-byte big-endian word at `0xffc`. Multi-byte fields are big-endian. Types: `enum`, `u8`, `u16`, `u32`, `i8`, `bitfield`, `bytes`. A map that declares any other checksum is refused, so the page never writes a wrong checksum. The second `<script>` is the task UI and only calls into the engine.

`../komaset.py` uses the same big-endian checksum (the card check's parity test runs both).

`testdata/demo-main.cur` is the owner's main-camera `PARAM.CUR` (2026-11-06, stock 2.40). `testdata/demo-spare.cur` is derived from it with 9 user settings and two camera-specific counters changed. `testdata/make_demo.py` builds the spare and embeds `settings-map.json` plus both blocks into the page between the `DEMO-EMBED` markers. **Rerun it whenever `settings-map.json` changes** (the parity test fails if the embedded copy is stale):

    python3 tools/komaset/web/testdata/make_demo.py [--main path/to/PARAM.CUR]

Open the page with `?demo=copy`, `?demo=edit` (two edits pre-applied), `?demo=mode`, `?demo=backup` or `?demo=looks` (Looks offline on the main settings file) to load the demo files and jump to that task; `?demo=1` loads the demo list only.

## Test

`python3 tools/komaset/web/test_web_parity.py` checks the checksum constants and code tokens, the big-endian codec, the merge rules, a Python reference checksum against the real block, that the embedded data matches `settings-map.json` and the fixtures, and that task text has no jargon or em dashes. It also runs `node --check` on the two scripts (alone and together), runs the overlay helpers (`ovLuma`, `ovHistogram`, `ovPaint`) in node on a synthetic frame, and checks `RCP_TABLE` against `bwrecipes`. For Set up a card and the app shell it checks the strings and wiring, that the embedded module hash equals the `koma04.grmod` line of `SHA256SUMS` (and, separately, that the module file itself still matches that line), the manifest (name, standalone, tokenless start, colours equal to the page tokens, valid PNG icons), `node --check` on `sw.js`, the JS SHA-256 against `hashlib` (including the module), and runs the card-check port in node on ten cards built from `demo-main.cur` (clean, refused import, no KOMALOG, unconsumed file with a wrong tag, low pool with lower-case names, stock settings with a partial log, and more), comparing every output line, verdict, summary and exit code with `verify_session.run` on the same files. It does not run the page; check behaviour in a browser with the demo URLs.

The USB side is tested in `../bridge/test_komabridge.py` (bridge endpoints against the mock) and end to end by `test_e2e_browser.py`: the real page in headless Chrome (Playwright; channel `chrome`, else Playwright's Chromium; skipped without either) against komabridge on `MockBody(tether=True).hw_timings()`. Nine tests: full-scale timings (a 20 s second-session arm with the waking line and no error before it ends, live view, a shot shown and live view back after it, two EV changes inside the 7 s busy window landing), settings read / edit / send, photos grid / lightbox / download, live mode switch 320 × 240 ↔ 160 × 120 and re-arm after a card read, unplug and replug (live view comes back), a real bridge process restart, two tabs without a fight, Remote (both layers, menu key, picture back), a shot showing up in Review photos and an interval run. Any page error or unhandled rejection fails the test. Run: `python3 -m pytest tools/komaset/web/test_e2e_browser.py` (about 2 minutes).
